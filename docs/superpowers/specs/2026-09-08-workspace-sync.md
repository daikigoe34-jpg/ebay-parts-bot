# Part Scout: device synchronization and resumable research

The user requested the necessary additions after discussing operating Part Scout through Work on a PC while starting on an iPhone. Implement private automatic cross-device saving and an explicit research queue. Preserve the current Japanese mobile UI, calculations, supplier limits, backups and offline behavior. No new paid API, seller OAuth, automatic purchases, listing, messages, or background supplier fetching.

## Product contract
- Main research settings/costs/work position, the standalone shipping draft, and a research queue have separate synchronized documents.
- Every edit saves synchronously on the device before any network activity. Pending changes survive reload/offline. Initial empty/default screens must not replace existing cloud data.
- Use Sites dispatch identity on the server (`oai-authenticated-user-id`), never a browser supplied owner ID. Each user has separate records. Missing identity returns 401, database failure 503; never a global fallback. Only same-origin JSON writes are accepted. Personal data and responses are never cached by the service worker or stored in the public git repository.
- Use revision comparison for all writes. Concurrent divergent edits enter a visible conflict state preserving both values. Do not silently choose by device clock or last response. Identical retries may resolve automatically. When choosing either version, retain the other in a durable local recovery copy and allow backup of both; fail safely if that recovery copy cannot be saved. A changed login must not upload a previous account's pending data.
- Show Japanese states for checking, device saved / waiting, synchronized time, conflict, authentication required, and unavailable/static hosting. Resume on load, online and focus/visibility, with bounded debouncing and no rapid retry loop. Re-renders and navigation metadata alone must not steal focused input or silently invalidate user edits.
- Queue: add an exact manufacturer/part, status (waiting to research / researching / needs confirmation / complete) and note; duplicate IDs cannot create duplicate work. Clear accessible actions resume a shipping estimate and retain per-item drafts when switching work. Queue progress is user-declared, never a shipping/purchase approval. Provide a copyable Work handoff instruction containing the live current page link, pending part/status and remaining verification, without secrets or invented API integration.
- Keep user-facing work simple: the queue is usable with eBay keys absent; lookup starts only on an explicit button; existing supplier gate still applies. An unavailable API means local-only functionality with truthful status, not data loss.
- Preserve old backup formats and localStorage keys; validate imported and synchronized data before use. Successful cloud receive invalidates pending lookup/import callbacks before applying UI state.

## Sync HTTP contract
`GET /api/workspace/{main|shipping|queue}` and `PUT` same path, fixed namespace allowlist.
GET 200: `{schemaVersion:1,userKey:string,revision:integer,data:object|null,updatedAt:ISO|null}`. A new document has revision 0, null data.
PUT JSON: `{baseRevision:integer,data:object}`. Required `Content-Type: application/json`, same-origin `Origin`, and `X-Part-Scout-User-Key` containing the exact userKey returned by GET. This header is an expected-account precondition, never an owner selector; compare it to the current authenticated identity before every write and return 403 `{error:"account_changed"}` for a mismatch (400 for an absent/malformed precondition). Browser fetch uses same-origin credentials and no-store. Production server uses the forwarded Sites user identity; local tests inject the trusted header only as a fixture.
PUT 200: same shape as GET with revision incremented. PUT 409: current remote shape plus `error:"revision_conflict"`; client preserves its local document. 401 `{error:"sign_in_required"}`, 400 invalid request, 413 over 2,000,000 UTF-8 bytes, 415 wrong media, 403 wrong/missing origin, 503 `{error:"storage_unavailable"}`. Responses have `Cache-Control: private, no-store` and no CORS.
Payloads are JSON objects with bounded shape/depth/strings; reject prototype keys. Server uses prepared SQL and atomic compare-and-swap. Client performs existing domain validation before applying remote data. Document cap is 2,000,000 request bytes (including envelope).

## Ownership and validation
The Site owner alone edits `/workspace/sites/part-scout-mobile`, calls Sites tools and publishes the same project. Client implementer edits only the original repository linked worktree. Root implements/integrates the backend in the Site and records server source in original git after client completion. Focus validation on two-device round trip, concurrent edits, stale GET/PUT, lost response retry, reload of pending edits, quota failures, account changes, malformed response, no-cache API, queue draft resumption and current shipping regression.
